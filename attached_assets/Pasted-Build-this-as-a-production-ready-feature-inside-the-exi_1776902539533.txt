Build this as a **production-ready feature** inside the existing Sortii meal planner app.

# Feature name

**Cook With What’s Already Here**

## Purpose

Create a low-energy dinner rescue feature for nights when the user has not shopped, money is tight, energy is low, and they need the app to suggest realistic meals from random ingredients already in the house.

This should feel like a **Sortii rescue tool**, not a pantry manager and not a formal recipe search engine.

The user should feel:

* relieved
* guided
* not judged
* able to get to a useful dinner answer quickly

---

# Product behaviour summary

## Pantry assumptions

Always assume these are available and do not require user entry:

* salt
* pepper
* cooking oil
* water

Treat these as default pantry staples in all matching and fallback logic.

# Data handling

## Existing recipe dataset

Use the current Sortii recipe dataset as the primary source of meal suggestions.

Do not replace the current recipe engine.
Reuse the dataset and matching structures where possible.

Each recipe should be scored against:

* ingredients explicitly entered by the user
* pantry assumptions: salt, pepper, oil, water
* selected night-style preferences

# Ingredient parsing requirements

## 1. Merge all input sources

When user taps CTA:

* collect guided prompt selections
* collect manually added chip items
* collect free text input
* merge into one ingredient input set

## 2. Parse free text

Extract likely ingredients and intent from free text.

Examples:

* “I’ve got eggs, cheese, wraps and frozen peas” → eggs, cheese, wraps, peas
* “Need something quick and cheap” → preferences: fastest, cheapest, low effort
* “Have random freezer veg and rice” → mixed veg, rice

## 3. Normalise ingredient names

Create a light normalisation / synonym map.

Examples:

* mince → beef mince
* ground beef → beef mince
* shredded cheese → cheese
* grated cheese → cheese
* frozen veg → mixed veg
* canned tomatoes → tinned tomatoes
* capsicum ↔ bell pepper
* tortilla wraps → wraps
* ramen noodles → noodles

Do not overbuild this. Keep it practical and extendable.

# Matching engine

## Matching priority

Always search internal recipe dataset first.

### Matching logic goals

Return the most realistic “yes, you can make this” options first.

### Suggested scoring model

Create a weighted score for each recipe.

Example score dimensions:

* ingredient overlap score
* required ingredient coverage
* missing ingredient penalty
* time preference bonus
* low effort bonus
* kid-friendly bonus
* one-pan bonus
* cheapest bonus
* fridge-use bonus

### Recipe categories

Classify results into these groups:

#### 1. You can make this now

Use when:

* all major recipe ingredients are present
* only assumed pantry basics are needed
* or only tiny optional items are missing

#### 2. Very close

Use when:

* recipe is missing only 1 to 2 non-essential or swappable ingredients

#### 3. Backup idea

Use when:

* internal recipe confidence is low
* or no internal recipe passes minimum threshold

---

# Scoring rule suggestions

## Ingredient weighting

Not all ingredients should be equal.

If your dataset supports it, distinguish between:

* core ingredients
* supporting ingredients
* pantry ingredients
* optional ingredients

If not, approximate this by:

* first few listed ingredients count more
* protein and base item matches count more
* flavour helper mismatches count less

### Example approach

* protein match: high value
* base carb/starch match: high value
* key vegetables: medium value
* sauces/extras: lower value
* assumed pantry basics: auto included, no penalty

## Missing ingredient tolerance

Allow:

* 0 missing major items for “You can make this now”
* 1 to 2 missing minor items for “Very close”

Do not show unrealistic matches.

If a recipe technically matches but clearly depends on a missing core ingredient, do not rank it highly.

---

# Fallback AI behaviour

## Trigger

Only use AI fallback if internal recipe matching is weak or empty.

Do not use AI fallback first.
Do not use external web search as the primary approach.

## Fallback purpose

Generate a simple improvised meal concept using the user’s ingredients and Sortii’s tone.

### Fallback constraints

The AI fallback should:

* use entered ingredients plus assumed basics
* keep it simple
* keep method short
* avoid fancy chef language
* avoid introducing lots of new ingredients
* favour low-cost, low-effort combinations
* sound like a useful rescue option

### Fallback output structure

Return:

* meal name
* why it works
* quick 2 to 4 step method
* rough cook time
* effort label

Example feel:

* **Cheesy Egg Wraps**
  Uses your eggs, wraps and cheese for a fast no-shop dinner.
  10 to 15 mins • very easy

## Future-ready note

Architect this so a future optional external recipe search layer can be added later if desired, but do not build that into the main flow right now unless it is already part of the app infrastructure.

# Tone rules

Keep all UI copy and outputs aligned to Sortii voice:

* warm
* lightly dry
* practical
* calm
* never too cute
* never bossy
* never shaming

Good examples:

* “Not glamorous, but still dinner.”
* “A decent no-shop-night option.”

* recipe blog enthusiasm

# Empty / low-input states

## If user enters very little

Do not dead-end.

Example response approach:

* prompt them gently that broader results work better with a few more ingredients
* still try to generate at least one fallback idea

Example:
**You’ve not given me much to work with, but here’s a rescue option.**

## If no internal match exists

Still return:

* one AI fallback idea
* optionally one small suggestion encouraging adding 1 to 2 more ingredients for better results
